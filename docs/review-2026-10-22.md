# Rumable 0.1.4 整体 review 与用户接入流程核对

后续修复：用户随后提供 0.1.4 Windows 实测失败证据并授权修复。0.1.5 已处理本报告两项问题，以及 IIS 输出污染、空排除条件、旧未完成事务恢复和 Windows 无交互检测；详见[修复与复测说明](windows-0.1.4-recovery.md)。以下保留首次审查时的结论，不能再据此理解为当前源码尚未修复。

审查日期：2026-10-22。源码基线：`c76054d70d6b48c9aaccfb5ac370f8fe7cdf442e`；本轮读取的公开 latest 清单同样指向 0.1.4 / 该提交。本轮修改用户文档与本地演示，不修改正式安装器、CLI 或页面生成器，也不覆盖已发布的不可变包。

## 结论与发现

### P2：Linux 一键命令可能将下载失败报告为成功退出

位置：[web/generator.mjs](../web/generator.mjs)，`makeCommand` 的 Linux 返回值（基线第 128 行）。

页面生成 `curl ... | sudo sh -s -- ...`。在未开启 pipefail 的 shell 中，如果网络、证书或 HTTP 错误让 curl 失败且没有脚本输出，sh 会执行空输入并返回 0；整个一键命令因此返回 0，没有安装和注入。用退出码判断自动化任务成功会误报。

本轮直接调用实际 `makeCommand` 生成命令，仅将 curl 替换成返回 22 的函数，将 sudo 替换成无提权转发函数；实测 curl=22、最终 pipeline=0，stderr 有模拟下载错误。不是依靠推测判断。

建议后续修复：生成器保证下载与执行失败都传递非零结果，例如明确使用具备 pipefail 的执行环境，或下载成功后才执行，并测试空下载、截断下载及网络错误。当前用户手册要求在 Bash 先开启 pipefail，再检查 CLI status/probe；这是操作规避，不是代码修复。

### P2：Windows 一键入口没有建立公共资源与私有状态的 NTFS 权限边界

位置：[scripts/install.ps1](../scripts/install.ps1) 的 `Invoke-RumableWindowsInstall`（基线第 136–142 行），以及 [storage.go](../internal/rumable/storage.go) 的 `atomicWrite` / `writeJSON`。

安装器创建程序目录后直接运行 setup；setup/render 创建状态与资源，但没有配置 NTFS ACL 或探测实际匿名文件读取身份。IIS 桥接创建虚拟目录并保留现有 handler/匿名设置，不负责赋予物理目录读取权限。`os.Chmod(0600)` 在 Windows 只控制只读属性相关位，不建立 Unix 式所有者读写权限；已核对本机 Go `src/os/file.go` 的 Windows 行为说明。

影响分两种条件：已有受限状态目录时，IIS 匿名读取者可能不能读取 SDK，enable 的资源探测失败并进入恢复；继承权限较宽时，也不能用“文件模式 0600”证明状态/备份只对管理员可读。不能把两种情况概括为所有 Windows 都安装失败或都存在相同 ACL。

建议后续修复：明确查询/选择读取身份，建立仅管理员/SYSTEM 管理私有状态、仅公共资源允许读取的 ACL，并验证失败恢复不扩大既有权限。需要原生 Windows/IIS 验收。本轮新增逐步 ACL 流程，注明自动安装前置条件；没有用 Linux 上的 PowerShell mock 冒充 NTFS/IIS 验证。

## 已修正的文档问题

- 原用户指南要求从“发布目录 README”找包，而公开 OSS 使用对象白名单，不提供该入口；改为 10 个平台包、清单及 SHA256SUMS 的直接链接。
- 区分完整 `[[sites]]` 配置与自动发现 `server + [rum]` 配置：后者只能给 setup --discover，不能直接执行 enable。
- 明确一键安装只保留 CLI，临时 TOML 会被清理；提醒留存下载配置及实际 auto-ID/state-dir。
- 手动流程使用固定绝对目录和显式 config/state-dir/site，说明初次 init/render 与后续 enable 的不同用途。
- 补充手动 Nginx 挂接没有自动 attach 原文件备份，不能承诺 rollback --attachment 自动撤销；卸载前需人工恢复相应 include/指令。
- Windows 清理命令原来指向发布包的 scripts 目录；改为对应源码目录，并说明无法访问 Git 不影响普通安装和手动验收。
- 去除可能让用户以为 Windows Nginx 可自动接入的 README 示例，明确 Linux/Nginx 与 Windows/IIS 的支持范围。
- 区分脚本安装成功、HTML 注入、浏览器实际请求和观测云入库，不将模拟接收端响应等同于真实入库。

## 审查路径与边界

| 用户路径 | 核对内容 | 结论/边界 |
|---|---|---|
| 下载/发布 | release 打包白名单、manifest、SHA256SUMS、install.sh/ps1、CI immutable/latest | 包含版本固定与摘要校验；无需 Git；旧不可变文件不会因文档修改而更新 |
| 页面配置 | generator/app、OpenWay/DataKit、完整/发现格式、版本能力检查 | 自动模式推迟到服务器选择目标；高级手动配置仍有必要 |
| 自动接入 | discovery → setup → prepare/attach/apply | 重用部署身份、选择后重查目标、歧义无终端拒绝；不自动安装 Web 服务器组件 |
| Nginx 注入 | include/handler、HTML anchor、路径/MIME/压缩、SDK 探测 | 常见静态/代理布局自动处理；复杂布局人工审查；目标外的配置语义不能一概保证 |
| IIS 注入 | Microsoft.Web.Administration、规则/映射/压缩、原生 bridge | 有事务及归属校验，ACL 缺口如上；本轮无 Windows 实机 |
| 启停/恢复 | apply/transact、资源校验、journal、rollback、uninstall | 失败保留恢复依据；普通回滚与挂接回滚分开；旧资源保留给缓存页面 |
| 权限/身份 | state-dir、site ID、binary/args、IIS site/application、外部漂移 | 目标绑定不能随意原地改名；不允许靠换 state-dir 接管 |
| OTel | 独立配置/组件开关、安装与卸载入口、依赖归属 | 页面/setup 只处理 RUM；本轮没有新增 OTel 端到端环境验证，沿用独立手册 |
| 用户验收 | status/probe、浏览器 SDK、上传、真实后端读回 | 四层证据分开；请求发出或模拟 204 不证明真实数据入库 |

当前测试没有暴露新的 Nginx 注入/启停/回滚失败，不等于穷尽所有服务器配置。IIS 原生提交与本地日志之间仍存在无法跨系统原子提交的窗口；实现保守保留事务并要求审查，不应宣传成任意故障都能无人工恢复。
